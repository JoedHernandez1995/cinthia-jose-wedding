# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Next.js 14 (App Router, TypeScript) rebuild of José & Cinthia's wedding invitation — a single-page site generated from an original visual design tool export. All content is in Spanish. It now also includes a guest-management admin system (Supabase-backed) for CSV guest import, per-guest personalized invitation links, view tracking, and RSVP management — see "Admin/guest system" below.

## Commands

```bash
npm install       # install deps
npm run dev       # start dev server at http://localhost:3000
npm run build     # production build
npm run start     # run the production build
npm run lint      # next lint
```

There is no test suite configured in this project. See README.md for Supabase setup steps required before the admin system works.

## Architecture — the invitation itself

The page is decomposed by feature/section rather than living in one file. `app/page.tsx` (root `/`) renders `components/HomeLanding.tsx`, a static teaser (monogram, couple names, date, a note that the invitation is personal) — it never shows the envelope or full invitation, since those require a guest's personal link. The full invitation lives at `app/i/[token]/page.tsx`, which renders `components/InvitationPage.tsx`, the composition root that renders every section top-to-bottom in a fixed order: envelope intro → nav → (guest greeting, if personalized) → hero → historia (story) → padres (parents' blessing) → cancion (song/vinyl) → photo marquee → detalles (venue + countdown) → rsvp → comollegar (location) → vestimenta (dress code) → faq → gift → recomendaciones → footer.

- `app/layout.tsx` — root HTML shell: Google Fonts (`Cormorant Garamond`), imports `app/globals.css`. Also sets the site-wide `metadata` (`metadataBase` from `NEXT_PUBLIC_SITE_URL`, plus `openGraph`/`twitter` using `siteMetadata.ogImagePath` — the proposal photo, reused from `hero-photo.webp`) that drives the WhatsApp/social link-preview card. `app/i/[token]/page.tsx` overrides this per guest via `generateMetadata` (title greets by `displayName`/`name`) — Next.js replaces the whole `openGraph`/`twitter` object per route rather than deep-merging, so that override repeats the image fields rather than just title/description. `generateMetadata` and the page component share one `getGuestByToken` call via `cache()` from `react`, and neither one records a view (that only happens on envelope-open, see `EnvelopeIntro` below).
- `app/globals.css` — self-hosted `@font-face` rules for `Poppins`/`Slight` (files in `public/fonts/`), CSS custom properties for colors/fonts (`--color-*`, `--font-*`), global resets. This is the single source of design tokens — there is no separate `theme/` directory.
- `components/HomeLanding.tsx` — root `/`'s static landing; not part of the invitation composition, has no `guest` concept.
- `components/InvitationPage.tsx` — composition root for the full invitation; owns section ordering, the shared page chrome, and threading the `guest` prop (see below) into `GuestGreeting`/`RsvpSection`. Each section otherwise owns its own copy and local state.
- `components/sections/*` — one component per section (e.g. `HeroSection`, `RsvpSection`, `GiftSection`), each paired with its own `*.module.css` file. Styling is CSS Modules throughout — no inline `style={{...}}` objects, no Tailwind.
- `components/ui/*` — small shared building blocks reused across sections: `Reveal` (scroll-reveal wrapper), `Photo` (image with placeholder fallback), `GoldDivider`, `GoldButtonLink`, `OutlineButtonLink`.
- `config/site.ts` — single source of truth for wedding facts, copy, contact placeholders, FAQ entries, and gift accounts. `config/family.ts` holds the parents' names.
- `hooks/*` — extracted stateful behavior: `useLiveCountdown` (ticks the wedding countdown), `useCopyToClipboard` (gift-account "COPIADO" toggle), `useRevealOnScroll` (single-element IntersectionObserver), `useEnvelopeAnimation` (intro open/close timing).
- `lib/*` — pure helpers with no React dependency: `buildWhatsAppLink` / `buildPlannerNotificationMessage` (`lib/whatsapp.ts`), `buildCalendarDownloadLink` (`lib/calendar.ts`, the `.ics` data URI), `lib/guests.ts` (server-only guest data access, see below).
- `types/invitation.ts` — shared types for the static invitation (`Faq`, `GiftAccount`, `RsvpChoice`, `CountdownUnit`). `types/guest.ts` holds guest/RSVP types, kept separate to avoid coupling the public invitation types to admin concerns.

### State model

State lives in the section that owns it — no global state management, no context:

- `EnvelopeIntro` (via `useEnvelopeAnimation`) — gates the intro envelope overlay; `open()` runs a timed close-then-reveal transition.
- `VenueDetailsSection` (via `useLiveCountdown`) — ticks every second to drive the countdown to the hardcoded wedding date/time.
- `Reveal` (via `useRevealOnScroll`) — each instance owns its own `IntersectionObserver`; once revealed it never re-hides.
- `RsvpSection` — always rendered with a `guest` prop in practice (`InvitationPage` only renders from `/i/[token]`), backing a real form persisted to the database. The `guest` prop stays optional in the type/component signature for now; there's no caller that omits it.
- `GiftSection` (via `useCopyToClipboard`) — tracks which gift account's "copy" button was last clicked, for the "COPIADO" label timeout.

### Images

`components/ui/Photo.tsx` renders `<img src="/photos/{id}.webp">` and swaps to a gray placeholder box (showing the `alt` text) `onError`, so missing files degrade gracefully instead of showing a broken image icon. `marqueePhotoIds` (in `config/site.ts`) lists the ids used by the scrolling marquee section (duplicated once in the render to create a seamless CSS-animated loop).

### Configuration / placeholders to know about

Several real values live in `config/site.ts` and are still placeholders per `README.md`:
- `WHATSAPP_NUMBER`, `plannerWhatsAppNumber`
- Bank account numbers in `giftAccounts`
- Wedding date/time (`wedding.dateTimeIso`) and venue name/location — also referenced by `calendarEvent` for the `.ics` download; both must represent the same instant if changed. `wedding.rsvpDeadlineIso` must likewise match `wedding.rsvpDeadlineLabel`.

Missing marquee photos (`marquee-1`, `marquee-4-b`, `marquee-5-b`) render as placeholders until matching `.webp` files are added to `public/photos/`.

## Admin/guest system

Backed by Supabase (Postgres + Auth). See README.md for one-time setup (create project, run `supabase/schema.sql`, create the single admin user, fill `.env.local`).

- **Data model**: one `guests` table (`supabase/schema.sql`) — name, optional `display_name` (family/group name shown on the invitation instead of `name`, e.g. "Familia Martínez"), WhatsApp number, email, `invited_by` (`"novio" | "novia" | "padres_novio" | "padres_novia" | null` — which side invited them: the couple themselves, or either set of parents, as siblings of each other, not nested under novio/novia), `guest_location` (`"local" | "extranjero" | null`, null treated as local — gates whether `LocationSection`/`RecommendationsSection` render at all and which `giftAccounts*` list `GiftSection` shows; see "Guest-location gating" below), `partySizeAllowed` (**total** people allowed including the named guest — NOT a plus-ones count; a guest + spouse is `2`), a unique `token` (their personal URL slug) and a separate `checkinCode` (door check-in QR, never the same as `token`), RSVP state (`rsvp_status`, `rsvp_attending_count`, and `primary_attending` — only meaningful when `rsvp_status = "yes"`; `false` means the named guest declined but named companions still attend, enforced by a CHECK constraint requiring it be non-null whenever status is "yes"), invite-sent tracking, confirmation-email status (`confirmation_sent_at`/`confirmation_send_error`), and rolled-up view stats (`view_count`, `first_viewed_at`, `last_viewed_at`). A `guest_companions` table holds each named plus-one as its own row (own `id`/`checkin_code`, matched across RSVP edits by normalized name); `guests.companionNames`/`.companions` are derived from it, never written to directly. A separate `guest_views` table logs each individual view. RLS is enabled with **zero policies** — all access goes through the service-role key server-side only, never through the anon/browser client.
- **`lib/supabase/{server,client,admin,middleware}.ts`** — `server.ts`/`client.ts` use the anon key for the admin's auth session (cookie-based via `@supabase/ssr`); `admin.ts` is the service-role client used exclusively by `lib/guests.ts` for all `guests`/`guest_companions`/`guest_views` reads/writes (imports `server-only` to make an accidental client-component import a build error).
- **`middleware.ts`** — gates `/admin/**` (except `/admin/login`) behind a valid Supabase Auth session, redirecting to login otherwise.
- **`lib/guests.ts`** — all guest data access: `getGuestByToken`/`getGuestById`, `listGuests`, `createGuest`/`updateGuest` (both throw `DuplicateGuestError` on a name+phone collision rather than an unhandled DB error; `updateGuest` also throws `GuestValidationError` and **blocks** lowering `partySizeAllowed` below the guest's already-confirmed companion count + 1 — fix the RSVP via override first), CSV parsing/upsert (`parseGuestCsvRows`, `upsertGuestsFromCsv` — an upload's blank `invited_by`/`guest_location`/`display_name` never clears a value already set in the admin panel, handled via separate targeted updates after the main upsert), `recordGuestView`, `submitRsvp`/`overrideRsvp` (validates companion count against `partySizeAllowed - 1` server-side, never trusts a client-sent count; delegates the write to the `apply_rsvp` Postgres RPC, which locks the guest row and applies the status/companion-sync/event-log writes in one transaction — closing a race where two concurrent submits could both read stale state, and rejecting a resubmit within its cooldown window with a `rate_limited` exception; also builds/sends the confirmation PDF+email via `lib/confirmation.ts`'s `sendGuestConfirmation`, which never throws), `checkInByCode` (same atomic compare-and-swap pattern, used by `/checkin/[code]`), `markInviteSent`, `regenerateToken`, `exportGuestsCsv`, `getGuestSideBreakdown` (counts by side × RSVP status, feeds the dashboard chart), and `buildGuestInviteLink` (wraps `buildWhatsAppLink` with the guest's `/i/[token]` URL baked into the message).
- **`lib/rateLimit.ts`** — `enforceRateLimit(key, max, windowSeconds)` calls the `check_rate_limit` Postgres RPC (atomic fixed-window counting in the DB, not in-memory) and throws `RateLimitError` past the limit; `ipRateLimitKey(scope)` keys by client IP + scope. Guards admin login (`app/admin/login/actions.ts`), RSVP submit/view-record/set-email (`app/i/[token]/actions.ts`), and the confirmation PDF download (`app/i/[token]/comprobante/route.ts`, limited both per-IP and per-token).
- **`lib/pdf.tsx`/`lib/qr.ts`/`lib/email.ts`/`lib/confirmation.ts`** — RSVP confirmation PDF+QR+email pipeline. Each confirmed person (guest + every named companion) gets their own QR encoding a `/checkin/{code}` URL; the PDF is emailed via Resend on every "yes" submit/edit. A send failure is recorded on the guest row and never blocks or rolls back the RSVP save itself.
- **`app/checkin/[code]/page.tsx`** — the door check-in page a staff member's phone camera lands on after scanning a guest/companion QR. `force-dynamic` so a re-scan of an already-used code always reflects the latest DB state rather than a cached response. `checkInByCode` (`lib/guests.ts`) looks the code up first against `guests.checkin_code`, then `guest_companions.checkin_code`, and marks it checked in via a conditional `UPDATE ... WHERE checked_in = false` (an atomic compare-and-swap — a losing concurrent scan just re-reads the winner's timestamp instead of erroring). Gated by the same admin auth as `/admin` (`middleware.ts` matches both), not public. Timestamps render via `lib/formatDateTime.ts` (`America/Tegucigalpa`).
- **`app/i/[token]/page.tsx`** — a guest's personal invitation. `force-dynamic` (always hits the DB). Looks up the guest and renders `<InvitationPage guest={...} />`; the view itself is *not* recorded here (see `EnvelopeIntro` below). 404s (via `not-found.tsx`) on an unknown token. Root `/` is unaffected — it renders `HomeLanding`, an unrelated static page.
- **`components/sections/EnvelopeIntro.tsx`** — the site's actual first screen (shown before the envelope is opened). When `guest` is set, shows their resolved `displayName`, "Tienes/Tienen una invitación" (plural iff `partySizeAllowed > 1`), and "VÁLIDO PARA N PERSONAS" (`N = partySizeAllowed`) — all guest-specific copy lives here, not in `HeroSection` (which stays guest-agnostic). It also fires the view-tracking `recordViewAction` Server Action (`app/i/[token]/actions.ts`) from the open-click handler — a view is logged when the guest actually opens the envelope, not merely on page load.
- **`components/dev/DebugPanel.tsx`** — debug overlay, rendered from `InvitationPage` only when the URL has `?debug=1` (`/i/[token]?debug=1`). Lets you toggle guest location and party size client-side to preview how sections render for different guest states, without touching the DB — actual RSVP submission still validates against the real `party_size_allowed`.
- **RSVP flow** (`RsvpSection.tsx` + `RsvpCompanionFields.tsx`, guest mode only): "Sí, asistiré" opens an inline companion-count selector (capped at `partySizeAllowed - 1` in the UI, re-validated server-side) with a name field per companion when `partySizeAllowed > 1` (email is already on file from the envelope gate); "No podré asistir" submits directly when `partySizeAllowed === 1`. When `partySizeAllowed > 1`, declining first asks "¿Alguno de tus acompañantes podrá venir aunque tú no puedas?" — "No, ninguno" submits a plain decline; "Sí, algunos sí" reuses the same companion-name form (with `minCompanions={1}`, so at least one name is required) and submits `status: "yes"` with `primaryAttending: false`. This is the one way to represent "the named guest declines but their named companion(s) still attend" — `rsvp_status` means "at least one person in this party is attending"; `primary_attending` (only meaningful when status is "yes") says whether the named guest themselves is among them. Submission calls the `submitRsvpAction` Server Action (`app/i/[token]/actions.ts`), which persists to the database — this is the source of truth. Responses are editable via "Editar respuesta" only until `wedding.rsvpDeadlineIso`; every "yes" submit re-sends the confirmation PDF (which, and the confirmation email's copy, omits the primary guest's own QR/wording when `primaryAttending === false` — see `lib/pdf.tsx`/`lib/email.ts`). Past the deadline, self-serve editing (or, for guests who never responded, the yes/no buttons themselves) is replaced by a message directing the guest to contact `faqContact.name` (the wedding planner) via a WhatsApp button (`whatsappMessages.rsvpLastMinute`), since changes after that point go through her instead of the site. There is no WhatsApp courtesy-notification step on a normal yes/no submit — the DB write is the only side effect.
- **Admin dashboard** (`app/admin/`): `/admin` (overview stats + `SideBreakdownChart`, a stacked bar per side showing confirmed/declined/pending, colors matching the guest-table status badges), `/admin/guests` (searchable table with a **Todos / Novio / Novia / Padres Novio / Padres Novia** side tab control — "Todos" is the union across all sides and the only tab where guests with no side assigned show up, since none of the 4 specific-side tabs is an exact match for them — and within the active tab, guests are grouped into four fixed-order sections: Confirmados, Pendientes · vieron la invitación, Pendientes · no han visto, No asistirán, each with a count in its header and shown even when empty; each "Sí" row shows a bulleted sublist of confirmed companion names under its RSVP badge — plus CSV upload, add-guest form, CSV export at `/admin/guests/export`), `/admin/guests/[id]` (detail: edit-guest form for name/display name/phone/side/party size, view history, companion names, confirmation-email status, PDF download link, manual RSVP override for guests who respond outside the site — including a "primary attending" toggle for the same "declined but companions attend" case as the guest-facing flow), `/admin/checkin` (day-of door-staff dashboard — see below). `app/admin/guests/actions.ts` holds the guest-management Server Actions; `app/admin/login/actions.ts` holds `login`/`signOut`.
- **`/admin/checkin`** (`app/admin/checkin/page.tsx` + `CheckinBoard.tsx`) — `force-dynamic` headcount view for door staff, separate from the QR-scan-target `/checkin/[code]` page. Lists only `rsvpStatus === "yes"` guests, flattened to one row per person (guest + each named companion), with a live "`arrived`/`expected` personas han llegado" stat (`expected` = sum of `rsvpAttendingCount`) and a name search box — the manual fallback for when a phone's camera/battery fails at the door. Sorted not-yet-arrived first, alphabetical within each group. Each row is a large tap-to-toggle button reusing the exact same `toggleGuestCheckedInAction`/`toggleCompanionCheckedInAction` Server Actions as the `/admin/guests` table (imported cross-route — no duplicated check-in logic). A guest whose `primaryAttending === false` (declined but their named companions still attend) is excluded from its own row entirely — only their companions appear.
- **Bulk actions & reminders in `/admin/guests`** (`GuestTable.tsx` + `BulkSendQueue.tsx`): row checkboxes + a "select all filtered" header checkbox feed a bulk action bar (shown once ≥1 row is selected) with three actions — "Enviar invitación (N)" and "Enviar recordatorio (N)" each open a `BulkSendQueue` modal listing the applicable selected guests one per row with an individual "Enviar" button (WhatsApp has no bulk-send API in scope, so this only streamlines the admin's own tapping — it does not automate sending); "Marcar invitación como enviada (N)" and "Asignar lado (N)" (a `<select>` of the 4 sides + "Sin definir", paired with `bulkSetInvitedByAction` → `bulkSetInvitedBy`) are both true bulk DB writes (`.in("id", ids)` updates), each gated behind `useAdminConfirm()` since they silently flip state with no per-row feedback. The reminder queue only includes selected guests with `rsvpStatus === "pending"`; excluded already-responded guests are called out in the modal's note. Selecting a filter that hides a selected guest prunes it from the selection automatically. `buildGuestReminderLink` (`lib/guests.ts`, mirrors `buildGuestInviteLink`'s displayName/plural greeting) also backs a per-row "Enviar recordatorio" button shown only for pending guests.
- **How WhatsApp is actually used** — there is no WhatsApp Business API/automated sending anywhere. Every touchpoint is a `wa.me` deep link a human has to tap send on: (1) admin sending a guest's personal invite link, single or via the bulk queue (also auto-marks `invite_sent`), (2) admin nudging a pending guest with a reminder, single or via the bulk queue (no DB field tracks this — it's fire-and-forget), (3) a guest manually contacting the planner about a last-minute RSVP change past the deadline. A normal yes/no RSVP submit does **not** trigger any WhatsApp message — the DB write is the sole side effect. WhatsApp numbers are never parsed for input; the personal `/i/[token]` page and its view/RSVP tracking are the only source of truth.
- **Guest-location gating**: `guest.guestLocation` (`"local" | "extranjero" | null`, null treated as local) is threaded from `GuestViewModel` and checked at the `InvitationPage` call site only — `LocationSection`/`RecommendationsSection` themselves stay guest-agnostic and are simply omitted from the tree entirely for local guests (`NavBar` filters its "RECOMENDACIONES" link the same way, to avoid a dead anchor). `GiftSection` takes `guest` as a prop and picks `giftAccountsLocal` (Honduran bank accounts) vs. `giftAccountsAbroad` (Venmo/PayPal) from `config/site.ts` — mutually exclusive, never both.

## Notes for editing

- Design tokens live in `app/globals.css` (`--color-*`, `--font-*` custom properties) — new UI in the invitation itself should follow the existing CSS Modules pattern using those variables (`--font-display` for headings, `--font-serif` italic for body copy, `--font-label` for uppercase/letter-spaced labels, `--color-gold` accent).
- **Admin UI (`app/admin/**`) intentionally uses neutral fonts only** — `--font-label` (Poppins) for everything, including headings. Do not use `--font-display` (cursive `Slight`) or `--font-serif` (italic Cormorant) in admin pages; those are reserved for the guest-facing invitation's romantic styling.
- Section anchors (`#historia`, `#detalles`, `#rsvp`, `#vestimenta`, `#recomendaciones`, `#faq`, defined in `config/site.ts`'s `sectionIds`) are linked from `NavBar` and used as scroll targets — keep a section's `id` and its `NavBar` entry in sync if renaming a section.
- The couple's display name and wedding metadata come from `coupleNames.full` / `siteMetadata` in `config/site.ts` — change it there once rather than in each section.
- Never import `lib/guests.ts` or `lib/supabase/admin.ts` from a `"use client"` file — both are server-only (enforced by the `server-only` package) since they use the Supabase service-role key.
